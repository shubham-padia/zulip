## Description
## Overview

While reviewing the scheduled message delivery path, I found that `try_deliver_one_scheduled_message` could leave a `ScheduledMessage` row with both `delivered=True` and `failed=True`. If `send_scheduled_message` succeeds (setting `delivered=True`) but a later step—such as `notify_remove_scheduled_message`—raises an unexpected exception, the outer handler was unconditionally setting `failed=True` as well, even though the message had already been delivered.

The existing `was_delivered` check prevented the user-facing failure notification in this case, but the underlying database state was still inconsistent.

## Fix

Check `was_delivered` before marking the message failed, so a message that was already delivered is never also marked failed. The unexpected-error branch still logs via `logging.exception` for observability.

## Not from a filed issue

This wasn't reported or filed beforehand — I found it directly while reading this code path. Flagging that context since there's no linked issue to reference.

## Testing

Added a regression test (`test_exception_after_delivery_notification_failure`) that mocks `notify_remove_scheduled_message` to raise after delivery, and asserts the message stays `delivered=True, failed=False`. The test wraps the assertion in `self.assertLogs(level="ERROR")`, since Zulip's test harness treats an unexpected ERROR-level log as a failure unless it's explicitly expected — this path does intentionally still log the error.

I wasn't able to fully provision the dev environment locally, so I relied on CI (all jobs passing) rather than a local test run.

## Open question

The `was_delivered` mitigation already prevents the user-facing failure notification. I haven't traced every downstream consumer of `ScheduledMessage.failed`/`delivered` to confirm nothing else assumes mutual exclusivity — happy to dig further if a reviewer knows of a specific consumer to check.
