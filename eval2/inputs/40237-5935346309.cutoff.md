## Description
Fixes: #34985

With the "Plain text" emoji theme, only the predefined statuses could be saved with an emoji. For any emoji chosen in the emoji picker, `update_the_status_emoji_for_our_user` skipped `emoji.get_emoji_details_by_name`, so the request went out with an empty `emoji_code` and `reaction_type`, and `check_emoji_request` rejected it with "Invalid emoji type." The issue says 404, but going by the server code it's a 400 with that message.

This PR always looks up the emoji details and keeps `emoji_alt_code` as a display flag only, which is how `user_status.set_status_emoji` and `reactions.ts` already build their emoji info. How status emoji are displayed with the plain-text theme is unchanged. That question is still open in [#design > status emoji with plain text theme](https://chat.zulip.org/#narrow/channel/101-design/topic/status.20emoji.20with.20plain.20text.20theme/with/2381247), where hiding them in the main app UI was suggested but not decided. The status modal still shows `:name:` for the selected emoji, since `status_emoji_selector.hbs` checks `emoji_alt_code` first.

#37967 fixes the same bug by adding an `include_emoji_details` parameter that its only caller always sets to `true`. This version removes the condition and adds a test.

The test is a Puppeteer test because `UserStatusSession` isn't exported, and `emoji_picker.ts` and `user_status_ui.ts` are both in `EXEMPT_FILES` in `tools/test-js-with-node`, so a node test would mostly exercise mocks. The new case in `web/e2e-tests/user-status.test.ts` switches to the plain-text theme, picks `:grinning:` in the picker, saves, and checks the buddy list. It uses a different emoji from the existing test's `:laughing:` because re-picking the current emoji leaves the Save button disabled.

**How changes were tested:**

Lint passes locally. Puppeteer's bundled Chrome is x86-64 only and my dev VM is ARM64, so I couldn't run the Puppeteer tests locally; the new test passed in this PR's CI. I haven't reproduced the bug by hand or checked that the new test fails on `main`, and I haven't manually tried other emoji types.

- **The root cause:**
`update_the_status_emoji_for_our_user` does not call `get_emoji_details_by_name` when the emoji is set in text emoji mode. This logic was added as a rendering optimization, since text mode only requires `emoji_name` for display. However the same `emoji_info` object is used when submitting the status to the server. As a result, the API payload is incomplete when the lookup is skipped.

- **Approach for solving this issue:**
Add a new parameter `include_emoji_details` (with default value false, keeping the existing optimization intact) to `update_the_status_emoji_for_our_user`, so that when the `emoji_info` object is built for submitting the status to the server `get_emoji_details_by_name` is called as well.
