## Description
Fixes: #34985

This follows the design @laurynmm added to the issue from [#design > plain text theme user status](https://chat.zulip.org/#narrow/channel/101-design/topic/plain.20text.20theme.20user.20status/with/2211597): status emoji are always shown as images, even with the "Plain text" emoji theme. Until now that theme showed status emoji as `:name:` text, which squeezed the user's name in the buddy list. Picking a status emoji from the emoji picker also failed to save, with "Invalid emoji type.", because `update_the_status_emoji_for_our_user` skipped looking up `emoji_code` and `reaction_type`.

The first commit removes `emoji_alt_code` from status emoji info and the `:name:` branches from the five templates that render status emoji, which also fixes saving. It builds on #35137 by @17AnuragMishra, who is credited as a co-author.

The second commit covers the rest of that design. With the plain-text theme, emoji that are still shown as images (the emoji picker, typeahead, and status emoji) now use the organization's default emoji set instead of always Google, falling back to Google if the organization's default is plain text too. The sprite sheet is reloaded when an administrator changes the default. This also changes the emoji picker and typeahead for plain-text users in organizations whose default is Twitter, so it's a separate commit in case that part needs more discussion.

**How changes were tested:**

- [CerealNotFound, collaborator, 2026-02-14, comment] @zulipbot claim

- **The root cause:**
`update_the_status_emoji_for_our_user` does not call `get_emoji_details_by_name` when the emoji is set in text emoji mode. This logic was added as a rendering optimization, since text mode only requires `emoji_name` for display. However the same `emoji_info` object is used when submitting the status to the server. As a result, the API payload is incomplete when the lookup is skipped.

- **Approach for solving this issue:**
Add a new parameter `include_emoji_details` (with default value false, keeping the existing optimization intact) to `update_the_status_emoji_for_our_user`, so that when the `emoji_info` object is built for submitting the status to the server `get_emoji_details_by_name` is called as well.
