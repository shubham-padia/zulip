### #19589 (issue, closed): Separate `command` and `text` field for slack-compatible outgoing webhook
Opened by esamson (NONE). Labels: area: integrations. Assignees: none.
Description: Discussed here: https://chat.zulip.org/#narrow/stream/127-integrations/topic/gitlab.20slash.20commands/near/1247658

Current behavior puts entire message, including bot mention, in the `text` field of the outgoing POST.

POST coming from Slack itself puts the "slash command" in a separate `command` field while their `text` field only contains the message body after the command.

For better compatibility, if message starts with a bot mention then we should separate that out into a `command` field and put the rest of the message in the `text` field.

Perhaps we can also transform the mention (`**@mybot**`) to a slash command (`/mybot`) so it looks like it would coming from Slack.

These two are different interfaces. Adding the `command` field would produce a payload matching neither format.
- [Niloth, 2026-09-07] | Field | Legacy outgoing webhook (Zulip emulates this) | Slash command | | ---------------------------------- | :----------------------------------------------: | :---------------------------: | | trigger_word, thread_ts, timestamp | ✓ | ✗ | | command, response_url | ✗ | ✓ | | trigger_id, api_app_id | ✗ | ✓ (added sometime after 2021) |

But `text` is the entire message content, including bot mentions. So, receivers must currently either be Zulip‑aware, or users must place the bot mention at the end of the message so that it is safely ignored.
