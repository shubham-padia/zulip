## Description
Users who configure [alert words](/help/dm-mention-alert-notifications#alert-words) currently have no way to find the messages that triggered them other than manually searching `is:alerted`. As discussed in the issue, the most valuable addition is a dedicated **Alert words** view in the left sidebar, parallel to **Mentions**, with an unread counter so it's easy to see and revisit conversations where an alert word appeared.

**This PR adds:**

- An **Alert words** row in the left sidebar's Views section (`is:alerted`), shown only when the user has at least one alert word configured. It appears and disappears live as alert words are added/removed.
- An unread counter on the row that live-updates as alert word messages arrive, are edited, or are read.
- A hover tooltip reporting the unread alert-word count, and a row popover menu linking to alert words settings.
- A first-class empty-narrow banner and navbar title/icon for `is:alerted`.

**API**

- `POST /register`: `unread_msgs` now includes a `watched_phrases` array, parallel to `mentions`.
- `GET /events` (`update_message_flags`): `message_details` now includes a `has_watched_phrase` boolean, parallel to `mentioned`.

**Changes since the previous PR state**

- Dropped the "message edits" notification commit [`949d4927b769d50c245a682e01133dad697f7b62`](https://github.com/zulip/zulip/pull/36764/changes/949d4927b769d50c245a682e01133dad697f7b62).
- Muted alert words now count : previously the frontend excluded them, so the initial count and live updates disagreed.
- Removed a duplicate `case "alerted"` in `narrow_banner.ts` .
- Fixed left-sidebar search : the Alert words row could show for users with no alert words after searching/clearing.
- Removed an obsolete test expecting the old generic `is:alerted` banner.
- Tidied the 9 commits into six coherent ones with rewritten messages.

- [Tim Abbott, 2025-04-07] I think on another thread we've discussed that this is not an API direction that makes sense.
- [Tim Abbott, 2025-12-10] So we have a more current effort working on this. The proposed API extends the `unread_msgs` data structure with: - A `has_alert_words` list adjacent to and parallel to the `mentions` list, containing the message IDs for unread messages with the `has_alert_words` message flag. - A `has_alert_words` boolean field on the `message_details` list in https://zulip.com/api/get-events#update_message_flags-remove, alongside the `mentioned` boolean field already present there.
- [Tim Abbott, 2025-12-10] I propose we use `has_watched_phrase` for these, since the plan in #28779 is to rename them to "Watched Phrases", and this will save us needing to migrate those parts of the API in the future. There's some risk that we fail to complete said renaming or change our mind, but I think overall it's going to make our life easier to just start with the expected longer-term name. @**Santhosh Kumar** FYI.
- [Tim Abbott, 2025-12-10] The one other risk with this API is that nothing in it says which word in the message is alerted/watched. We have an unsolved problem with that for highlighting alert words in messages, but I think it doesn't actually impact this API, which is just about determining which message IDs are relevant for doing unread counts and the like.
