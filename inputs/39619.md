## Description

# 1st commit

When moving messages/topic to a channel with different access permissions, we execute either 4 queries or 2 queries.

1. When one channel is **private** and the other is **web-public**: 4 queries.
2. When **only one**  of the channels is **private** or **web-public**: 2 queries. 
## Changes

Replace the 4 `.update()` calls with a single efficient raw SQL query that reproduces the exact behvaior:

- No queries are executed when both access permissions match.
- Only the relevant column/s  is/are upated according to which access permission differs. 

## Execution time difference
### Data setup
A realm with 
 - `6k` users.
 - `3,472` total Attachments.
 - `17,756` total Messages. 

The function simulates exactly (only for the "relevatn" update attachment part) moving a topic with `436` messages, `2` archived (deleted) messages, `434` attachments, and `75` archived attachments. 

I tested against the first case (4 queries) using  `%timeit -n 1000 -r 10 function()` essentially running each one **10k** times:

#### Results
 - Main (4 ORM queries) -->  **43** ms
 - PR (single raw query) --> **9** ms	

A reduction in execution time by **80%** and PR is **4.7x** faster than main !


# 2nd commit

In `do_update_message`, only `user_profile_id` and `flags` fields for  `UserMessage`s are needed, so we replace the full rows fetch with just those two.

This is significantly more efficient when moving a  topic/message in large streams. For example, a stream with **20k** results in fetching **20k**  `UserMessag` rows. We now fetch 2 fewer columns from the large `UserMessage` table and avoid building full ORM objects in memory for potentially thousands of rows.

## Execution time difference
Code setup that simulates fetching 20k rows and doing the real work done in `do_update_message` :

```python
# Main
def fetch_ums():
    ums = UserMessage.objects.all()[:20_000]
    usage = list(map(user_info, ums))

# PR
def fetch_ums():
    ums = UserMessage.objects.all()[:20_000].values_list("user_profile_id", "flags")
    usage = list(map(user_info, ums))
```
Tested using `%timeit -n 100 -r 10 func()`, running each function 1k times

### Results
 - Main -->  **386 ms**
 - PR   --> **74 ms**

A reduction in execution time by **80%** and PR is **~5x** faster than main !


# 3rd commit
In `do_update_message`, when moving messages to another stream, we feth both the old and new subscriber sets and took their difference in Python resulting in **2** queries and building two large sets of user IDs.
  
We compute that difference in db via `exclude()` with a single query instead. This removes one round trip, and constructs one set only.
    
## Execution time difference
Running the relevant code block where old stream has `12k` subscribers and the new stream has `7k`  subscribers:
Difference between **commit** and **main** is **negligble**; running ` %timeit -n 300 -r 5 code_block()`, commit is faster by 3-5 ms, the main gain is one fewer db round trip and avoiding constructing a large `set()` in Python.

# 4th commit
Inside `update_user_topic_visibility_policies_on_move`, we call `get_users_with_user_topic_visibility_policy` twice: one for target (stream, topic_name) and another for original (stream, topic_name) resulting in two separate queries.

**Changes:**  Replace the 2 calls to that function with a single parallel helper  `get_users_with_user_topic_visibility_policy_on_move` which executes a single query and ORs the two pairs, matching the exact same rows fetched by the two calls to the original function.

# 5th commit
More of a cleanup, consistency, and being Python idiomatic than a real performance gain.
