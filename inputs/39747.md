## Description
Split out of #39513, per Karl's suggestion to review and deploy the error pages and the emails separately. This is the error pages half; the emails are in #39746.

Design discussion: [#design > error pages](https://chat.zulip.org/#narrow/channel/101-design/topic/error.20pages/with/2495177).

The error pages used old marketing styling: a bordered card on a mint background, with illustrations that didn't match each other or the page they were on. This restyles them as a "system surface", where the page, header, and footer share one tone and the error content is centered on a recessed band. It also gives every page an illustration that says what went wrong.

The surface follows the reader's color scheme, using `light-dark()` pairs like `portico_variables.css` and the redesigned emails already do.

**Illustrations.** The 19 error pages map onto seven situations, based on what the user can do next. Each situation has one drawing:

| Illustration | Pages |
|---|---|
| Not found | 404, link does not exist, link malformed |
| Expired | link expired, realm creation link invalid, account deactivated |
| No access | 403 (CSRF), auth subdomain, realm creation disabled, demo creation disabled |
| Rate limit | rate limit exceeded, remote server rate limit exceeded |
| Update needed | unsupported browser, insecure desktop app |
| Server error | 500, 405, and the static 5xx fallback pages |
| Self-hosted | remote realm server mismatch, both remote billing login errors |

The 403 and 405 pages had no art before. The old hourglass, `400art.svg`, and `500art.svg` are removed.

Each drawing has a separate light and dark SVG in `static/images/errors/`, picked with `<picture>` and `prefers-color-scheme`. An earlier version of this PR inlined monochrome art and colored it with `currentColor`. The new drawings use several colors per theme, which `currentColor` can't express. Loading them as files also keeps the art out of the templates. A small `error_page_art` macro holds the markup and each drawing's dimensions, so the page reserves space before the art loads.

The static 5xx pages reference the files by their `/static/` path, as they did `500art.svg`, since nginx serves those even when the app is down.

**Dev gallery.** Most error pages are hard to trigger in development, so the last commit gives every error template an `/errors/<slug>/` URL and adds `/devtools/error_pages/`. That page shows all of them as clickable previews, grouped by illustration. It's independent of the redesign, so I'm happy to split it into its own PR if that's easier to review.

### #39746 (PR, open): Restyle the HTML emails.
Opened by dnlklmn (MEMBER). Labels: size: XL. Assignees: none.
Description: Restyle the HTML emails.

Split out of #39513, per [Karl's suggestion](https://chat.zulip.org/#narrow/channel/413-kandra-design/topic/emails/near/2494534) to review and deploy the emails and the error pages separately. This is the emails half; the error pages are in #39747.

Design discussion: [#design > HTML emails](https://chat.zulip.org/#narrow/channel/101-design/topic/HTML.20emails/with/2495179)

Replaces the teal email chrome with the same "system surface" design: one surface tone, content on a rounded card, the Zulip wordmark centered above it, and filled call-to-action buttons. Since every email now shares the wordmark header, the per-email `{% block illustration %}` overrides and the swimming-fish footer image are gone. The old illustration assets stay in `static/images/emails/`, because already-sent emails link to them.

Emails are light by default. Clients that support `prefers-color-scheme` get the dark variant; clients that ignore it keep the light design, which avoids the unpredictable auto-inversion that email clients apply to dark-by-default emails. This is the approach Karl proposed: a light theme that always looks good, dark as progressive enhancement.

The messages-style emails (digest, missed messages, support requests) render without this chrome and are unchanged.

**The first commit is a bug fix that stands on its own.** `css_inline.CSSInliner` deletes the `<style>` element after inlining, which silently drops *every* `@media` rule from sent email — so the responsive rules already in `email.css` have never reached recipients. That's a pre-existing bug on `main`, not something this PR introduces. `keep_style_tags=True` fixes it, and it's also what makes the dark color scheme possible at all: without it the `prefers-color-scheme` block would ship and reach nobody.
