- [Greg Price, 2021-12-31] `set -u` is probably better to have than to not have. (Then you explicitly say `"${foo:-}"` or whatever, with the `:-`, when you do want to allow the variable to be unset.) But I think its impact is a lot smaller than that of `set -e` -- I think the number of bugs it's likely to affect is much smaller, if you're writing reasonable code in the first place.

- [Greg Price, 2021-12-31] `set -o pipefail` is also often helpful but I feel like I've run into situations where it caused problems that were a pain to work around (which contrasts with `set -e` and `set -u`, where the solution when the behavior it causes isn't what you intended is to add a few more characters that make your intent explicit.) I guess a comment on that gist has an example: https://gist.github.com/robin-a-meade/58d60124b88b60816e8349d1e3938615#gistcomment-4012229

- [Greg Price, 2022-01-18] To the substance of your question: unfortunately, I think there is not a simple way to reliably do so, and I think the same thing is true of `set -u`. If the script doesn't use pipelines at all then it's not affected by `set -o pipefail`, but pipelines are a very commonly-used shell feature so I expect that wouldn't help for very many scripts (and there'd still be the matter of `set -u`.) And of course the point of using `set -o pipefail` is to have it where it *can* have an effect on behavior, so applying it to the scripts that never use pipes wouldn't get us very far into resolving this issue anyway.
- [Greg Price, 2022-01-18] I think the steps for adding these flags will look basically like: * Understand the shell programming language. * Understand what the specific features `set -u` and `set -o pipefail` change in the shell's behavior. * For a given script, read it line by line, and asking at each bit of code: Could those flags cause an error here? Under what conditions would they do so? What would the non-error behavior be in those conditions? Could that non-error behavior be desirable? * Most of the answers will be: no, they can't at this line; or yes, they can, and that's good because the non-error behavior would be nonsense. * Occasionally the answers will be: yes, they can, ooh and actually that'd be bad be [...]
- [Greg Price, 2022-01-18] Note those first two steps, though. I think this issue is one that will probably only make sense for someone to take who has spent some time writing shell scripts before.
