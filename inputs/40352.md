## Description
Caught by @Alexis211 in #40097: gogs and gitea deliver `issue_comment` events for comments on both issues and pull requests, distinguished by whether `payload.issue.pull_request` is null (issue comment) or a non-null stub (PR comment). The gogs handler — which gitea reuses end-to-end — ignored the distinction and formatted every such event as an issue. 

This PR fix mirrors the pattern the GitHub webhook already uses: a shared `is_pull_request_comment_event` decides both the topic's `type` field and the `type=` argument to the body-rendering helper.

Description: Gogs/Gitea/Forgejo use the same event type `issue_comment` both for issue comment and PR comments. This adds a disambiguation pathway so that messages for PR comments are properly generated.

**Remaining concerns:**

I added a unique disambiguation logic for all three software (Gogs / Gitea / Forgejo). By inspecting the JSON payloads of my issue tracker (Forgejo) and the fixtures in the repo for Gogs / Gitea, I'm confident that this check will work for all three of them. However it might be the case that the webhook format for Gogs/Gitea has evolved and this check no longer works.

In all cases, I believe that the situation with this PR is better than the situation before, as at least some cases of issue comments actually being PR comments will be caught successfully.

Note that Gitea and Forgejo have an additionnal `is_pull` field in the root JSON object which would provide a better disamiguation pathway, unfortunately it is not available on Gogs according to the fixtures in the repo.
