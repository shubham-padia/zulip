## Description
Fixes: stale `get_user` cache entry keyed by a user's old email address after they change `email_address_visibility`. There's no issue filed for this.

Moving into or out of "Everyone" visibility switches `UserProfile.email` between the real and dummy addresses, but the cache entry under the old address never gets deleted. `bulk_change_user_setting` writes the setting with `bulk_update` (no `post_save`) and defers `bulk_flush_users` to `on_commit`, when the object already has the new email. The `save(update_fields=["email"])` that follows flushes only the new address too.

For up to a week after someone hides their email, `get_user` keeps finding them by their real address. That affects `/avatar/{email}`, the `sender:` and `dm:` search operators, and DMs addressed by email. `GET /users/{email}/presence` fails with a 500, because the cached user's `email` no longer matches the presence rows it looks up.

The fix flushes the user's caches before the email changes, which is what `do_change_user_delivery_email` already does.

I ran into this while checking #40088. The `do_scrub_realm` path reported there is already covered: `do_scrub_avatar_images` saves each user before their email is scrubbed, and the `post_save` flush from that save still sees the original address.

One open question: as in `do_change_user_delivery_email`, the flush happens inside the transaction, so a concurrent request could re-cache the old row before commit. I kept the existing pattern instead of adding an `on_commit` delete for the old key, but can switch if you'd prefer that.

### #40088 (issue, closed): do_scrub_realm doesn't invalidate memcached UserProfile entries keyed by the pre-scrub email (stale PII survives up to 7 days)
Opened by tritsystem (NONE). Labels: none. Assignees: none.
Description: **Found via a property-based audit** (copy/clone independence, cache-invalidation consistency) run across several widely-used Python libraries; the cache-key-level repro below was written and independently re-run before filing.

## Summary

`do_scrub_realm()` (`zerver/actions/realm_settings.py:805-822`), which overwrites `full_name`/`email`/`delivery_email` with anonymized placeholders when an organization owner requests deletion, relies solely on `UserProfile`'s `post_save` signal to invalidate the per-user memcached entries. That signal computes cache keys from the *already-mutated* instance — i.e. the new scrubbed placeholder — never from the real pre-scrub identity. So any memcached entry keyed by the user's real (pre-scrub) email/delivery_email is never invalidated by scrubbing, and would keep serving the real PII (full name, email) until its normal TTL (7 days, see the `cache_with_key(..., timeout=3600 * 24 * 7)` decorators on `get_user`/`get_user_profile_by_id` etc. in `zerver/models/users.py`) expires on its own.

This is the same *class* of gap as #39347 (leftover PII after user deletion) but a different mechanism (application cache, not a DB table) and a different code path (`do_scrub_realm`, not `do_delete_user_core`).

## Root cause

- `zerver/lib/cache.py:596-612` (`delete_user_profile_caches`) computes the cache keys to delete from `user_profile.email` / `user_profile.delivery_email` **as they are on the instance passed in**.
- `zerver/lib/cache.py:673-682` (`flush_user_profile`, wired via `post_save.connect(flush_user_profile, sender=UserProfile)` at `zerver/models/users.py:991`) calls `delete_user_profile_caches` with the *just-saved* instance — by the time `post_save` fires, `instance.email`/`instance.delivery_email` already hold the new value.
- Contrast this with the one call site that gets it right, `do_change_user_delivery_email()` (`zerver/actions/user_settings.py:117-129`): it explicitly calls `delete_user_profile_caches([user_profile], user_profile.realm_id)` **before** mutating `user_profile.delivery_email`/`email`, so the pre-change identity's cache entries are correctly busted (the post_save signal then also busts the new identity's, which is typically a no-op).
- `do_scrub_realm()` has no equivalent pre-mutation call — it mutates `user.email`/`user.delivery_email` directly to the scrubbed placeholder and then calls `.save(update_fields=[...])`, so only the (never-before-cached) placeholder's keys get invalidated.
