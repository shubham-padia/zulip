## Description
Fixes: #40239

Temporary file access tokens are hex-encoded signed strings. Valid hexadecimal
input can still decode to non-UTF-8 bytes, which currently turns a malformed
unauthenticated URL into an internal server error. Treating that specific
decode failure like the other invalid-token cases preserves valid-token
behavior and returns the existing `Invalid token` response.

There are no differences from the issue plan and no remaining decisions or
concerns. The exception handling intentionally catches `UnicodeDecodeError`
rather than a broader exception.

### #40239 (issue, open): Non-UTF-8 temporary file access tokens return HTTP 500
Opened by sdivyanshu90 (CONTRIBUTOR). Labels: area: uploads. Assignees: none.
Description: An unauthenticated temporary file URL returns HTTP 500 when its token is valid
uppercase hexadecimal but decodes to non-UTF-8 bytes.

### Steps to reproduce

1. Run the development server from current `main`.
2. Request `GET /user_uploads/temporary/FF/file.png` without authentication.

### Observed behavior

The request returns HTTP 500. `base64.b16decode("FF")` produces `b"\xff"`,
then `.decode()` raises `UnicodeDecodeError`, which is not handled.

### Expected behavior

The endpoint should return the existing `Invalid token` JSON error, as it does
for other malformed tokens.

### Proposed fix

Handle `UnicodeDecodeError` alongside the existing invalid-token exceptions and
extend the endpoint test to cover a non-UTF-8 token. This does not change valid
token behavior.

I found no matching report after searching open and closed issues and pull
requests for the endpoint, decoding exception, and token-handling code.
