## Description
To support the #34441, clients need a cheap way to know how much file upload space an organization is currently using. Today the only API source is  `GET /attachments`, which actually fetches metadata on every file the user has ever uploaded which is far too expensive to poll for a banner.

This PR adds the current usage directly to the `POST /register` response as `realm_upload_quota_used_bytes`, which clients can combine with `realm_upload_quota_mib` to display quota usage.

**Note:** The value is computed by `Realm.currently_used_upload_space_bytes()`, which is memcached (**7-day TTL** per create and delete of attachement) and **costs only two quick indexed queries on a cache miss**. Since it is not entirely free, it is gated on the `attachment` `fetch_event_type` instead of the always-present `realm` one, so clients don't have to pay unnecessary.

Attachment events already carry `upload_space_used`, so `apply_event` live-updates the registered value from those events, keeping a long-lived event queue's state consistent as files are uploaded and deleted.

Fixes #36648.

Completes @sayamsamal's work in the PR #36084

### #api design > used upload space
https://chat.zulip.org/#narrow/channel/378-api-design/topic/used.20upload.20space
- [Tim Abbott, 2025-11-12] So in #36084, we're trying to add a helpful banner about the situation where an organization has used most of its file upload quota, before it's hit the limit. The function to compute that value is kinda expensive (it combines a daily analytics value with adding the sizes of new files uploaded that day), with a cache that gets flushed every time a file gets uploaded in the organization. Currently, the only data source through which we expose that information is `GET /attachments`, which also does a likely more expensive thing (fetching metadata on all the user's lifetime uploaded files). So we should not use that.
- [Tim Abbott, 2025-11-12] Would it make sense to just add an `upload_quota_used` type key in the `POST /register` response?
- [Greg Price, 2025-11-12] Sounds like a good plan. Maybe named like `realm_upload_quota_used`? Could imagine having in the future a concept of per-user upload quota, which the shorter name would sound like it meant.
- [Tim Abbott, 2025-11-12] Hmm, I just did some performance testing on Cloud. For random realm IDs, it typically takes ~50ms on a cache miss; goes down to <0.3ms on a cache hit. I've seen some quite a bit longer values, some over 500ms.
- [Tim Abbott, 2025-11-12] I bet that can be fixed though; rather than deleting from the cache, for example, we could store in the cache an object with a bit more metadata, and do deltas off that, rather than from the start of the day.
- [Tim Abbott, 2025-11-18] Filed #36648 for this. @**Alex Vandiver|12178** I'd appreciate your help with figuring out why `currently_used_upload_space_bytes` is sometimes expensive when run on random Realm IDs; it's might be that it's a statistics problem or something, and not something we should be making code changes to address.
