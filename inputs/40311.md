## Description
Previously the call-creation endpoints did not validate that the caller's `realm.video_chat_provider` matches the endpoint being hit, so any authenticated user could create rooms on any provider the server had credentials for, including from realms with `video_chat_provider` set to "Disabled".

This change gates each provider's creation endpoint on `realm.video_chat_provider` and returns a clear "organization is not configured to use ..." error otherwise.

 **Open question:**

 For now this PR treats the two Zoom providers (`zoom`, id 3;`zoom_server_to_server`, id 5) as distinct: each endpoint branches on `VIDEO_ZOOM_SERVER_TO_SERVER_ACCOUNT_ID` and requires the realm's `video_chat_provider` to match the specific id for the server's configured mode. An alternative would be to accept either Zoom id as "Zoom is enabled"
 and then branch on the server setting to pick OAuth vs. server-to-server.
 I am not sure what is more aligned with Zoom use.  `web/src/compose_call.ts` and the `VIDEO_CHAT_PROVIDERS`  use the same name for both:
https://github.com/zulip/zulip/blob/f862fd0b9cdfb5bebad878e94d7e592ea744fb9d/zerver/models/realms.py#L665).

CZO: https://chat.zulip.org/#narrow/channel/127-integrations/topic/Server-side.20enforcement.20of.20.60realm.2Evideo_chat_provider.60/with/2529164

The realm setting effectively gates the compose-box UI in the web client, but the server accepts calls to any endpoint whose provider is configured, regardless of what the realm has selected. Is this by design, or something we'd want to fix [...]
- [Niloth, 2026-09-23] I don't think it's deliberate, but I can't be sure. We could add that check for all of them, but we're not risking anything by leaving it out?
- [thedance, 2026-09-24] I think one problem is that some of the video providers (Galène, Nextcloud Talk, Constructor Groups) use server-wide admin credentials to provision on the external service. Only admins can choose which video provider their users can use, but now that setting isn't enforced server-side. So any authenticated user in any realm, including realms with `video_chat_provider = disabled`, can create rooms/groups on the shared instance under the server's admin creds. Could this be a problem? Whatdo you think?
- [Niloth, 2026-09-24] Yes, my thinking was that all someone can do is create meetings, they can't actually use the credentials for anything else. So, why would anyone bother sending API requests for that?
- [Niloth, 2026-09-24] But, there has been a recent user request (#40156) about restricting access to call creation, so it might make sense to add those checks, like you're saying.
