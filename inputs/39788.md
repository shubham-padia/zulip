[the comment thread](https://github.com/zulip/zulip/pull/39764#issuecomment-5031876561).
No changes from that PR other than rebasing onto current `main` —
the commit is an unmodified cherry-pick of the one already reviewed
and tested there.

Zulip's S3 upload backend opens a `GetObject` on an object while the
tusd pre-finish hook simultaneously issues a self-`CopyObject` on
that same object, to update its Content-Type and Content-Disposition
after upload. AWS S3 doesn't mind this, but S3-compatible backends
that use per-object locking for consistency (MinIO, as reported in
the issue) hold a read lock for the duration of the open
`GetObject`. The concurrent `CopyObject` then blocks until MinIO's
write-deadline timeout tears down the idle reader, which is a
constant ~30 second stall on every upload above roughly 100 KB.

The object was only ever opened to sniff its charset, and that
sniffing only applies to `text/plain` content. So the fix opens the
object at all only when that's actually needed, explicitly closes
that read before the self-copy runs, and opens a fresh, unrelated
read afterwards for attachment creation/thumbnailing. This keeps no
read open across the self-copy, regardless of backend.

**How changes were tested:**

- Same regression test as #39764, asserting the pre-finish hook
  opens the object twice (once to sniff, once fresh afterwards) and
  explicitly closes the sniffing read, rather than holding a single
  read open across the self-copy.
- This commit is an unmodified cherry-pick of the one already merged
  and reviewed on #39764, where full CI (backend tests on Debian
  12/13 and Ubuntu 22.04/24.04/26.04, mypy, CodeQL) passed and
  @amanagr confirmed manual testing looked good. It applied cleanly
  onto current `main` with no conflicts.

### #39752 (issue, closed): S3 backend: tus pre-finish hook stalls ~30s per upload on MinIO due to unclosed GET on the object it self-copies
Opened by dutty5 (NONE). Labels: bug, area: uploads. Assignees: none.
Description: ## Summary

On a self-hosted Zulip with the S3 uploads backend pointed at MinIO, every file upload
larger than ~100 KB hangs for a constant ~30 seconds between "transfer complete" and the
file URL being inserted into the compose box. The stall happens inside
`handle_upload_pre_finish_hook` (`zerver/views/tusd.py`).

The root cause appears to be that the hook opens a `GetObject` on the just-uploaded
object via `attachment_source()` and never reads or closes the streaming body for
non-text files, then issues a self-`CopyObject` on the same object while that GET is
still open. MinIO holds a read lock on the object for the duration of an active GET, so
the copy blocks until MinIO's write deadline kills the idle reader (~30 s). AWS S3 does
not lock this way, which is presumably why this has gone unnoticed.

## Environment

- Zulip Server: 12.1 (git deployment), S3 uploads backend
- Object storage: MinIO RELEASE.2025-10-15T17-29-55Z (single node, single drive), no
  versioning, no SSE on the uploads bucket
- Uploads via the web app (tus/tusd path)

## Symptoms

- Upload progress bar completes quickly; the object is fully present in the bucket.
- The client then waits minutes for the link to be inserted into the message. During
  this time tusd is waiting on the pre-finish hook response.
- The delay is a constant ~30 s per upload regardless of file size (2.3 MiB and larger
  files behave the same), while small files (~100 KB) complete in a few hundred ms.

## Investigation

`server.log` shows the pre-finish hook taking 30.5 s with almost no DB time:

```
2026-07-15 10:31:30.744 INFO [zr] 127.0.0.1 POST 200 30.5s (db: 4ms/4q) /api/internal/tusd (9@root via Go-http-client)
2026-07-15 10:32:45.594 INFO [zr] 127.0.0.1 POST 200 391ms (db: 5ms/5q) /api/internal/tusd (20@root via Go-http-client)
```

`mc admin trace -v` on MinIO shows the corresponding self-CopyObject (2.3 MiB object)
with `TTFB 30.16 s` and only 274 B up / 232 B down — i.e., the time is spent inside
MinIO waiting, not transferring:

```
[REQUEST s3.CopyObject] PUT /chat-uploads/2/.../IMG_9299.mp4
X-Amz-Copy-Source: chat-uploads/2/.../IMG_9299.mp4
X-Amz-Metadata-Directive: REPLACE
[RESPONSE] [ Duration 30.161673s TTFB 30.161628914s ↑ 274 B ↓ 232 B ]  200 OK
```

However, replaying the exact same self-`CopyObject` with boto3 outside the hook (both on
a single-PUT object and on a multipart object created by tusd) completes in 0.05–0.3 s.
